# Plan: v0.6 config, study planning, and artifact identity

**Status:** implementation plan; design decisions and source-scope validation required before broad migration  
**Scope:** Configuration ownership and explicit model/fit requests (#4), validated studies and dependency planning (#5), and fit-problem versus execution identity (#7).  
**Explicitly excluded:** Systematic-study orchestration/algorithm unification (#6). The plan may define shared identity and task contracts, but it does not migrate systematic methods into the study planner.

This plan is based on the current YAML, `qpym2.cfg`, `qpym2.storage`,
`qpym2.studies`, runner, and example-study implementations. It separates
observed behavior from the target design and identifies the decisions that need
to be settled before implementation.

## 1. Current architecture and findings

### Configuration (#4)

The live `config/config.yaml` composes four useful tiers: environments, staging,
analysis, and models. `config/staging/default.yaml` defines a broad preselection
and source patterns; `analysis/base.yaml` defines shared cuts/components; and
`models/tech_note.yaml` defines geometry/binning and some model overrides.

The separation is not consistently used by runtime code:

- The legacy `qpym2/run/run_create_staging.py` is marked deprecated as staging
  generation will be revised later.
- Single unified configuration system: `config_builders_new.py` and
  `hydra_adapter_new.py` have been promoted to canonical `config_builders.py`
  and `hydra_adapter.py`; all entry points and runners point to the unified 4-tier
  setup. Obsolete `hyperparams` references and probes have been eliminated.
- Silent model fallbacks have been removed: `_get_model_key()` enforces strict
  resolution (supporting `defaults.model_key` or `default_model` without arbitrary
  first-model fallback), and `StudyPoint` defaults to `"default"` without hardcoding
  concrete model values. `get_comp_cfg()` requires a valid `model_key`.

The four tiers remain the stable foundation, with typed request schemas
for operation-level values. Do not put run metadata into the statistical fit
definition merely because it is configurable.

### Study assembly (#5)

Current authored studies live in `studies/example_co_shift/`,
`example_bias_study/`, and `example_sens_study/`. They provide a reference,
sweep axes, and (for toys) study settings. `qpym2.studies.assembly` expands all
axes as a Cartesian product. `StudyPoint` implements model key, cut, shift, and
blinding fields; additional sweep fields can be stored in `params` without
necessarily changing an operation. Assembly defaults the model key to
`tech_note_200` if it is absent.

`Study` supports input checks/generation, fit execution/collection, and bias and
sensitivity toy methods. Its saved manifest is an input/point inventory rather
than an immutable resolved campaign plan. It does not describe a full artifact
dependency graph, task commands, run settings, seed roles, or task lifecycle.
The current fit loop iterates points; TSV generation and scheduler execution
are separate in `scripts/gen_params.py` and shell/SLURM helpers.

### Artifact and fit identity (#7)

Current template UUIDs are 12-character truncated SHA-256 hashes over staging
version, cuts, and transforms. Geometry is represented by parent directories;
the source name is intentionally not part of the hash payload. The current
staging version is a config value, not an ID for a resolved stage plus its raw
inputs.

Current fit UUIDs hash template UUID references, smoothing, priors, ROI
settings, **and MCMC settings** (`chains`, `draws`, `tune`, `target_accept`).
Consequently sampler effort changes the fit UUID. Effective model component
grouping is not reliably resolved because the selected `model_key` is not
passed to `get_comp_cfg()`. Prior settings record sample counts/modes but do not
identify a realized random prior sample or its complete generation provenance.
Cache checks generally test whether a file exists; they do not validate its
manifest/schema or whether its recorded sampling run meets requested quality.

## 2. Target configuration/request model (#4)

### Ownership

| Concern | Owner | Identity role |
|---|---|---|
| Physical roots, credentials/mount conventions, output locations | Environment profile | Path resolution only; machine-specific values are not scientific identities. |
| Raw-to-staged cuts, branches, transforms, output schema and source roles | Staging specification | Determines staged payload; paired with named raw source identities. |
| Shared physics cuts/constants/component conventions | Analysis specification | Enters downstream resolved input/fit specs only where consumed. |
| Named geometry/analysis model: ROI, threshold, binning, model overrides | Model specification | Enters every downstream product it changes. Production requests name the model explicitly. |
| Likelihood, smoothing, prior construction and other posterior-target choices | Fit specification/profile | Defines `fit_problem_id`; resolved effective values and prior references matter. |
| Sampler, chains, draws, tune, target acceptance, initialization, posterior seed | Run profile | Execution metadata and cache-quality policy; does not define the posterior target. |
| Toy type/design, injection distribution/range, toy-generation seed | Study/toy request | Scientific toy-generation identity; its fitted result has a separate fit problem and run profile. |
| Nominal point, intentional variations, requested products | Study specification | Defines comparison intent and dependency plan, not payload ownership. |

Add a typed/validated fit specification and run profile. Whether both are Hydra
groups or whether some values remain embedded in a study is an implementation
choice; their semantic ownership and identity boundary must remain explicit.
Use Python structured schemas as the field/type/default/validation source of
truth, with Hydra YAML supplying values and named profiles. Establish and test
one override order, for example profile defaults < study values < explicit
invocation overrides. The resolved request must record effective values and
their origins.

### Decisions/data needed before implementation

- Inventory each effective fit/input/toy setting, all consumers, current
  defaults, and whether it changes a persisted scientific payload, posterior
  target, or only execution quality.
- Decide the explicit model-selection contract for production APIs and whether
  a no-model config remains supported for configuration inspection only.
- Specify model override inheritance (especially components) and validate the
  fully resolved component list before fitting.
- Define the prior recipe and source identity: JAGS input/version, sample
  selection, covariance source, any random seed, and whether realized prior
  samples are persisted or deterministically reconstructed.
- Decide which configuration defaults are public supported defaults and which
  legacy fallback branches are removed. The full call-site inventory remains
  in [`../todos/v0.6_sundry_config.md`](../todos/v0.6_sundry_config.md).

## 3. Validated study definitions and dependency planner (#5)

### Study schema

Replace permissive point expansion with a typed `StudySpec` containing:

- study identity/description and explicit environment, staging, analysis,
  model, fit-specification, and run-profile selections;
- one resolved nominal/reference request;
- an explicit list of field paths the study varies and explicit point values;
- expansion mode (`explicit` or a deliberately requested Cartesian product);
- requested products/tasks, their dependencies, and required external
  references;
- toy design and role-named scientific seeds where applicable.

Do not accept arbitrary field names and silently retain them. Reject unknown
variation paths, invalid profile/model names, duplicate points, and
incompatible values during study assembly. A field can only be varied when a
registered operation consumes it and its downstream consequences are known.

### Initial dependency/invalidation map

Use this as a starting hypothesis; verify each selection's exact source scope
and persisted payload before implementing the planner.

| Changed value | Expected invalidation | Validation still needed |
|---|---|---|
| Raw file set, branch/schema contract, staging cuts/transforms | New staged artifact(s), then affected downstream products | Source identity policy; verify all staging filters/derived columns. |
| Model ROI/threshold/coverage | Affected observation/template histograms and input set; not raw staging if within stage coverage | Confirm how event-coordinate observations and ROI selection are persisted. |
| Histogram binning | Affected template histograms/input set; reuse observation event arrays if representation/selection is unchanged | Current coordinate directory partitions data and templates together; prove safe sharing before changing paths. |
| `co_cut`, `ndbd_cutoff` | Only payloads whose source/observation selection actually consumes the cut, plus input set and downstream fit | Current `create_storage_inputs_for_point()` builds `common_cuts` and passes them to data and template generation; define intended per-source cut scope before migration. |
| `co_shift`, `ndbd_shift` | Co-60 template or signal template respectively, then input set and fit | Confirm transform formulas, targets, and zero-shift identity behavior. |
| Components, likelihood, smoothing, prior definition | Fit problem/result only; reuse compatible input set | Ensure effective model override and prior-source identity are recorded. |
| Sampler settings / posterior seed | New execution or execution-quality upgrade for same fit problem | Define minimum cache quality and replacement/versioning policy. |
| Toy generation recipe/seed/index | New toy experiment, then toy-fit result | Define stable toy IDs and role-specific seed derivation. |
| Blinding/data source | New data context/observation and downstream input/fit products as applicable | Confirm blinding boundary and current staged/observation handling. |

The table is not a license to infer dependencies from setting names. The
resolved operation graph must declare which payload consumes each value.

### Planner and manifest

Plan the graph once from validated resolved specs. The planner should:

1. Validate point compatibility and each changed field against declared
   `vary` paths.
2. Resolve artifact identities and share identical upstream products across
   points; avoid expanding unrelated dimensions.
3. Emit a human-readable dry-run: point/task totals, dependencies, cache
   state, reused/new artifacts, seeds, profile settings, and outputs.
4. Write an immutable resolved manifest containing the authored intent,
   resolved config/specs, point/task IDs, task commands, upstream/output IDs,
   role-named seeds, and state/provenance records.
5. Generate local/SLURM/packed scheduler input from that manifest. Scheduler
   formats are execution adapters, not independent task definitions.
6. Resume only when artifact manifests and task state validate. `force` or
   rebuild creates a new execution/revision under a defined policy rather than
   silently replacing completed artifacts.

Keep specialized procedures free to define their own task graphs. This plan
does not force every systematic method into the study schema's ordinary sweep
executor; it specifies shared validated identities, task records, and
provenance contracts only.

### Decisions/data needed before implementation

- Enumerate supported study point fields and map each to its operation
  specification and invalidation edge.
- Clarify cut scope using concrete event/template examples; compare current
  storage input behavior with legacy `create_m2uv` behavior.
- Define canonical point/task IDs independent of YAML ordering and list index;
  define how IDs handle duplicate/equivalent points.
- Define deterministic scientific-seed derivation by study, point, operation,
  and toy index, distinct from posterior sampling seeds.
- Decide what task states are persisted, how interrupted/incomplete outputs are
  detected, and what constitutes a valid resumable artifact.
- Decide whether manifests are stored with studies, in the artifact store, or
  both, and which location is authoritative.
- Identify active notebook consumers and replace hard-coded path/point
  reconstruction with a manifest-reading helper.

## 4. Fit-problem identity, execution identity, and cache policy (#7)

### Identity graph

Separate the scientific object being computed from attempts to compute it:

```text
data context + raw source identities + resolved staging contract
  └── staging_id
       ├── observation_id
       └── template_id(s)
             └── input_set_id (exact observation/template member references)
                   └── fit_problem_id
                         └── execution_id / result bundle
```

- **`staging_id`:** canonical resolved stage contract plus named raw-source
  identities. It must not include downstream ROI, binning, smoothing, or study
  labels unless staging's stored payload changes.
- **Observation/template IDs:** canonical effective payload settings plus
  named upstream IDs. Include every selection, transform target/scope, and
  representation/geometry value that can change that payload. Preserve reuse
  for genuinely identical source-level templates.
- **`input_set_id`:** exact observation and template member IDs and the resolved
  input contract consumed by a fit. It is a composition identity, not a copied
  payload owner.
- **`fit_problem_id`:** input-set ID plus resolved likelihood/model version,
  effective components, smoothing, priors and prior-input references, and all
  other settings that change the posterior target. Hash resolved values and
  upstream IDs, not just a profile/model label.
- **`execution_id`:** a particular sampler/run profile and attempt for a fit
  problem. Record sampler, chains, draws, tune, target acceptance,
  initialization, posterior seed, software/source revision, host/job/retry,
  start/end times, and diagnostics here. These do not change `fit_problem_id`.
- **Scientific randomness:** a generated toy, blinding injection, randomized
  systematic sample, or stochastic prior realization is a scientific input.
  Give it a role-specific ID derived from the generation recipe and seed (or
  persisted realized payload), then reference it from the consuming input or
  fit problem. Do not treat its seed like a posterior sampler seed.

### Required corrections to current hashing/caching

1. Remove MCMC configuration from the scientific fit-problem hash. Preserve it
   in the execution manifest and implement a cache-quality policy for
   satisfying a requested run profile.
2. Pass the selected model key through fit setup and hash the **effective**
   resolved component grouping. Reject missing/invalid groupings instead of
   falling through to a different model or hard-coded component list.
3. Include resolved prior semantics and named prior-input provenance. If prior
   samples are stochastic and differ, identify their realized values or their
   deterministic recipe/seed as a distinct prior input.
4. Replace `staging.version` as a proxy for actual staged data with a stable
   `staging_id` and reference it through template/observation manifests.
5. Ensure binning/geometry and actual edge/schema identity are represented at
   the input/template boundary, rather than relying on an unvalidated directory
   name. Determine which coordinate-path partitions can safely be shared.
6. Validate cache hits against manifest schema, operation contract, upstream
   IDs, and payload integrity—not path existence alone. Use convergence
   diagnostics and configured minimum chains/draws as run-quality policy.
7. Define immutable result publication and `force`: a better run should create
   an execution revision or bundle and an explicit preferred-result reference,
   not silently overwrite an immutable result.
8. Version identity schemas and retain a compatibility reader for existing v0.6
   UUID-based artifacts. Store the complete canonical identity in authoritative
   metadata; a shortened hash is an address, not sufficient provenance.

### Decisions/data needed before implementation

- Fix identity key sets and serialization/versioning policy for staging,
  observation, template, input set, fit problem, toy, and execution objects.
- Choose collision handling and address length; determine whether a catalog is
  required to resolve truncated hashes to complete manifests.
- Choose payload checksum policy, including the distinction between raw-file
  checksums, whole-artifact checksums, and embedded manifests.
- Confirm filesystem atomic-publish capabilities and the storage layout for
  immutable artifacts/results.
- Set cache acceptance policy: required profile minima, R-hat/ESS thresholds,
  absent-trace behavior, and selection of the preferred execution.
- Specify how old v0.6 artifacts lacking complete manifests are read and
  classified (trusted legacy, import/verify, or cache miss).

## 5. Implementation phases and verification

1. **Schema/inventory:** inventory effective config fields and consumers;
   decide source scopes, model inheritance, prior provenance, identity keys,
   seed roles, and cache policy. Add schema-level validation without importing
   ROOT or requiring mounted data.
2. **Resolved configuration:** implement typed staging/input/fit/run/study
   specs, one explicit model-selection path, one path-resolution boundary, and
   the documented override precedence. Add tests for valid/invalid composition
   and model overrides.
3. **Identity foundations:** implement canonical, versioned identities and
   manifests; add immutable publication and validation. Test that raw source or
   stage-contract changes alter `staging_id`, while downstream-only changes do
   not.
4. **Fit identity split:** add `input_set_id`, `fit_problem_id`, and execution
   records. Test that sampler-only changes preserve the fit-problem ID and
   target-changing inputs do not. Verify model-specific components and
   stochastic prior provenance.
5. **Study planner:** implement explicit `vary`, supported expansion modes,
   dependency sharing, dry-run summary, and immutable manifest. Test unknown
   axes, non-Cartesian points, shared templates, cut scope, seeds, interruption,
   and resume.
6. **Incremental consumer migration:** route one representative fit study and
   one toy study through the new APIs; compare generated arrays, fit setup, and
   summaries to fixed synthetic/reference fixtures. Keep legacy readers during
   migration.
7. **Runner retirement dependency:** once parity and scheduler generation from
   plans are proven, retire the runner/TSV/config glue listed in
   [`../todos/v0.6_sundry_config.md`](../todos/v0.6_sundry_config.md). Do not
   redesign systematic-study algorithms as part of this plan.

### Acceptance criteria

- Every production request resolves to validated typed specs with explicit
  model selection and inspectable effective values.
- Study assembly rejects unsupported fields and produces a dry-run dependency
  plan and immutable manifest with stable IDs, seeds, and outputs.
- Identical scientific requests reuse staging, inputs, and fit-problem identity
  as appropriate; changed operation inputs create new identities only at the
  affected layer.
- Sampler-only changes are represented as separate executions of the same
  fit problem. Cache decisions are based on recorded quality/provenance.
- Existing v0.6 artifacts remain readable under a documented migration policy.
- Fit and toy consumers use the resolved API; the legacy-runner retirement
  prerequisite is met without changing the systematic-method scope excluded
  above.
