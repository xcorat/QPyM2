# Fit Data Layer Specification

- **Status:** Implemented (Core Storage & I/O Modules)
- **Audience:** QPyM2 engineering team
- **Scope:** Derived fit inputs, fit setups, fit results, and toy-fit products. Staged files are fixed upstream dependencies and are not redesigned here.
- **Plan:** [`todos/fit-data-layer.md`](todos/fit-data-layer.md)
- **Implementation:** [`qpym2.storage.identity_profiles`](file:///data/cuore/Analysis/M2/QPyM2x/qpym2/storage/identity_profiles.py), [`qpym2.storage.fit_data_store`](file:///data/cuore/Analysis/M2/QPyM2x/qpym2/storage/fit_data_store.py), [`qpym2.io.fit_data`](file:///data/cuore/Analysis/M2/QPyM2x/qpym2/io/fit_data/__init__.py)

## 1. Terminology

| Term | Meaning in this layer |
|---|---|
| **Observed data / observation** | Event-coordinate data used as the observed sample in a fit. Use `observation` as the object kind; use “data” in user-facing descriptions where natural. Blinded and unblinded arrays are distinct observations when their contents differ. |
| **MC sample / simulation** | The Monte Carlo source or sample from which a template is derived. The staged MC files are upstream inputs to this specification. |
| **Template** | A histogram payload consumed by the fit. Background MC templates are source-specific; the NDBD signal template is a separate role. Do not use “simulation” as the name for the derived histogram. |
| **Fit setup** | A resolved input-set reference plus the fit-level specification: components, smoothing, likelihood, and prior construction. |
| **Fit result** | The persisted output of fitting observed data: fit-component products and posterior trace, linked to its fit setup. |
| **Toy experiment / pseudo-experiment** | Generated pseudo-data and its generation specification. It is separate from a fit to that pseudo-data. |
| **Toy fit** | A fit result whose observation is generated by a toy experiment. |

“Measurement” is not the preferred name for event arrays: it usually suggests a measured scalar or already-aggregated quantity. Use “observed data” for the event sample. “Template” is the preferred name for the histogram representation used in the likelihood; preserve MC/signal provenance as metadata.

## 2. One store, organized by object kind

Use one configured store root. Organize files under kind-specific folders within that root; do not create separate stores for observations, inputs, or results. Keep inputs and results in separate folders. Model names provide aliases rather than physical ownership.

```text
<fit_store>/
  catalog.sqlite                 # optional, disposable index
  observations/observation-<id>.h5
  templates/template-<id>.h5    # source-level background or signal template
  prior-inputs/prior-<id>.h5     # optional persisted chain/sample products
  inputs/input-<set-id>.h5       # set metadata and object references; no copied payloads
  fits/fit-<id>/                 # one atomic result bundle
    fit.h5                       # fit payload plus embedded manifest
    fit.nc                       # trace; records fit ID/input-set ID in global attrs
  toy-experiments/toy-<id>.h5    # only when generated pseudo-data is retained
  toy-fits/toy-fit-<id>/
    fit.h5
    fit.nc
  views/<campaign-or-model>/     # optional aliases/indexes; never payload copies
```

This layout uses one store root and one HDF5 file per independently reusable observation/template by default. A fit result is a directory bundle because `fit.h5` and `fit.nc` must be published together; the directory can be installed atomically. HDF5 shards are an optional packing optimization if file counts or access benchmarks justify them. In that case, object IDs still resolve to individual datasets in immutable shards; do not append concurrently to shared shards.

### 2.1 Embedded manifest policy

For HDF5 payloads, store the canonical manifest inside the file, under a reserved namespace such as `/_qpym2/manifest_json`. It should contain the object ID, kind, identity profile/version, resolved identity values, relevant metadata, upstream object IDs, and creation/provenance fields. For a fit bundle, `fit.h5` is the canonical manifest carrier; `fit.nc` should at minimum carry matching `fit_id` and `input_set_id` global attributes.

An input-set HDF5 is a small composition descriptor: its manifest lists member object IDs and set metadata. It does not copy observation/template arrays. The fit reader resolves those references. If legacy callers require one monolithic input HDF5, materialize it as a compatibility/cache product keyed by the input-set ID; it is not the canonical set representation.

Sidecar manifests are not required for these self-describing HDF5/NetCDF artifacts. A catalog/indexer reads embedded manifests; a generated sidecar may be provided as a convenience for shell tools, but is not a second source of truth. Formats that cannot carry the required metadata may use a sidecar. A whole-file checksum cannot be stored inside the same file without a self-reference; keep it in the catalog or compute checksums over payload datasets/logical content instead.

Embedding metadata keeps it with the payload and avoids one extra inode per object. The tradeoff is that generic discovery must open each container, and metadata updates require rewriting the file. Therefore write the complete payload and manifest to a private temporary file, validate and close it, then atomically publish it. Published objects remain immutable.

## 3. Reusable object contracts

### 3.1 Observation

An observation object contains event-coordinate values and enough metadata to interpret them. Its identity distinguishes data variants and any selection that changes the stored array. Metadata records the coordinate names/units, effective selection, observed/blinded role, payload schema, and optional per-dataset checksums.

### 3.2 Template

A template object contains a histogram array with its role and source association. Store background MC histograms at source granularity, not at fit-component granularity. Store the signal template independently. Record axis interpretation, actual bin edges or an edge reference, normalization/source metadata, effective cuts, and applicable transforms.

Component grouping, normalization aggregation, and smoothing that occur during fit construction do not alter the source-template object. If a transform is applied while building a persisted template, that transform must be represented in its identity.

### 3.3 Input set

An input set is a named composition of object references, not another owner of copied payloads. Its manifest contains:

- one observation reference for the selected fit data;
- a mapping of source roles/names to background-template IDs;
- a signal-template ID;
- the geometry/edge metadata needed to assemble the fit input;
- the resolved input schema and input-affecting settings;
- optional compatibility-materialization metadata.

The set ID must distinguish different effective compositions. Reuse the same set when its resolved member references and input contract match, regardless of model label. Component lists belong to the fit setup, not the input set.

### 3.4 Fit setup and result

A fit setup references one input set and specifies the likelihood problem, component grouping, smoothing, prior method/parameters, and other fit-affecting choices. The resolved component list and other descriptive values may be recorded in metadata; any choice that changes the posterior target must also be represented by an identity key or a versioned fit-profile reference.

A result manifest records the fit-setup ID, input-set ID, output roles/files, and run metadata. `fit.h5` may retain fit-specific grouped component products used by plotting/toy utilities. The raw observation should be referenced by the input set rather than copied into every result unless a verified consumer requires a compatibility copy.

Prior inputs are fit dependencies, not source-template data. If sampled JAGS-chain values or generated priors are persisted, represent them as a reusable prior-input object or an explicit fit-setup dependency. Record the source identity and sampling/generation recipe, including a seed when it changes the scientific prior values.

## 4. Reversible object IDs and defaults

Object IDs identify normalized key/value descriptions and must be convertible both ways:

```text
normalized JSON / key-values  <->  object ID
```

An ID is not required to be a hash. A versioned, canonical, path-safe encoding is acceptable. A hash-only value is insufficient unless an authoritative registry maps it back to the complete identity description; payload checksums are separate from object IDs.

Each object kind has a versioned identity profile defining:

- the identity keys used for that kind;
- canonical types and value normalization;
- defaults for identity keys omitted by the caller;
- the profile/ID-format version required to decode the ID.

The encoding procedure is:

1. Validate supplied keys against the selected identity profile.
2. Fill omitted identity keys from that profile’s defaults.
3. Canonicalize the complete resolved key/value mapping.
4. Encode the mapping together with object kind and profile version into the ID.
5. Decode using the exact profile version carried by the ID and return the resolved mapping.

Defaults are explicit, reviewable, and immutable once used to issue IDs. Adding keys or changing defaults requires a new profile version; old IDs continue to decode using the old profile. Metadata may contain additional fields not used in the ID. However, if an extra field changes the scientific payload, the identity must include a corresponding value, key, or versioned profile reference. For example, actual edge arrays may be stored in metadata while the identity includes the binning/edge-profile key; the resolved component list can be stored as metadata while the fit identity includes the component-definition key.

## 5. Composition and compatibility API

The fit path resolves an input-set ID into ordinary arrays and metadata. Existing scientific code should continue to receive its required arrays/tables without needing to know their physical shard locations.

The interface should provide these operations conceptually:

- resolve an object ID to its manifest and payload/dataset location;
- resolve an input-set ID to observations, source templates, signal template, and geometry;
- optionally materialize a conventional `input.h5` for a unique input-set ID;
- resolve a fit-result ID to `fit.h5` and `fit.nc` plus its manifest;
- resolve toy-experiment and toy-fit IDs independently.

The compatibility materializer is a view/cache of a composition, not the canonical store. It must be keyed by input-set identity and reused across model labels. Fit execution must consume the input-set reference recorded in the result manifest rather than independently reconstructing a path from model parameters.

### 5.1 Additive I/O modules

Implement new modules alongside the current `qpym2.io` modules. Do not refactor or replace `io/hdf.py`, `io/fit.py`, `io/bkg_model.py`, `io/toys.py`, `io/syst.py`, or `io/csv.py` as part of the initial data-layer implementation. New runners and notebooks can opt into the new API; legacy callers continue to use the existing functions.

| New module | Responsibility |
|---|---|
| `qpym2/storage/identity_profiles.py` | Reversible object-ID encode/decode, per-kind identity fields, versioned defaults. Do not alter the v0.6 hash codec in the initial rollout. |
| `qpym2/storage/fit_data_store.py` | Resolve IDs to the single-root kind-specific paths; write temporary HDF5/result bundles, validate, publish atomically, and reject replacement of completed objects. |
| `qpym2/io/fit_data/embedded_metadata.py` | Read/write the canonical JSON manifest in HDF5 and stable identity attributes in NetCDF. Reuse current schema types where compatible. |
| `qpym2/io/fit_data/objects.py` | Typed `Observation`, `Template`, and optional `PriorInput` readers/writers for individual HDF5 objects. |
| `qpym2/io/fit_data/input_set.py` | Read/write metadata-only input-set HDF5 descriptors; resolve member objects; return the current fit-input tuple; optionally materialize a legacy-style `input.h5`. |
| `qpym2/io/fit_data/fit_result.py` | Publish/read fit result bundles containing `fit.h5` and `fit.nc`, with embedded manifest/IDs. |
| `qpym2/io/fit_data/legacy.py` | Import existing bundled `input.h5` files into objects/sets and provide compatibility exports using the unchanged legacy APIs. |
| `qpym2/io/fit_data/__init__.py` | Public exports for the new object and set APIs. |

Keep filesystem layout and atomic publication in the storage layer; keep HDF5/NetCDF serialization in the I/O layer. The I/O objects accept resolved paths or a store interface and do not construct paths from model labels.

The initial compatibility contract for `InputSet.read()` is equivalent to the current `qpym2.io.fit.read_input()` result: background source table, signal table, selected observed array, and edge metadata. `InputSet.materialize_legacy()` may call the unchanged `qpym2.io.hdf.write_input()` to create a compatibility bundle. New fit execution uses resolved object references directly.

`fit_result.py` should reuse `qpym2.io.fit.write_fit()`/`read_fit()` where their existing HDF5 and NetCDF layout is suitable. For example, write to a private temporary bundle with `data=None`, embed the result manifest after the legacy writer closes the files, validate that the unchanged reader still opens them, then publish the complete bundle. This avoids duplicating existing fit serialization logic while keeping the old functions unchanged.

## 6. Identity examples

The identity graph follows affected products:

```text
observation_id + source_template_ids + signal_template_id + geometry
                         │
                         └── input_set_id
                               │
                               + fit specification / prior dependencies
                               └── fit_setup_id
                                      └── fit result(s)

toy generation specification + reference fit/input
                         └── toy_experiment_id
                               └── toy_fit result(s)
```

Expected sharing behavior:

- A component-grouping or smoothing change reuses the input set and creates a different fit setup/result when it changes the fitted problem.
- A Co-shift variation replaces only the affected background-template reference; unaffected observations/templates and geometry remain shared.
- An NDBD-cutoff variation replaces the signal-template reference while retaining unaffected members.
- A binning variation replaces affected templates and geometry, while retaining an unchanged observation.
- A selection or blinding change creates a different observation and whichever templates it affects.

These are identity expectations; the current NDBD-shift implementation must be verified before treating its generated templates as distinct.

## 7. Migration and validation

1. Define the identity profiles and defaults from resolved current configurations; include examples showing ID encode/decode and old-profile decoding.
2. Add the new storage resolver and embedded-metadata adapter. Keep staged files as read-only upstream inputs for this work.
3. Add observation/template object readers and writers, then input-set composition and the legacy materializer. Do not modify existing I/O modules.
4. Add the fit-result bundle reader/writer and verify the HDF5 manifest and NetCDF identity attributes.
5. Route one fit runner and its result readers through the new APIs. Preserve old APIs and path-based artifacts; compare new input reads against `io.fit.read_input()`.
6. Import existing input bundles with the new legacy adapter, then add toy-experiment/toy-fit handling after nominal fits use the new contracts.

Required checks include ID round-trips with omitted/defaulted keys; stable decode across profile versions; the sharing cases in §6; no duplicate observation/template payloads across compatible sets; input-HDF5 compatibility; and result-manifest lineage to the exact input set. Storage packing and read performance should be measured before selecting one-file-per-object versus HDF5 shards.

## 8. Out of scope

- Staging transformations, staged-file format, and staging identity.
- Replacing ROOT/HDF5/NetCDF or introducing a new workflow scheduler.
- A required database/catalog redesign. A catalog may index the object and set manifests, but it is not the source of identity or payload data.
