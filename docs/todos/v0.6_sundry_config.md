## 1. Raw source paths and staging configuration

### Current state

- `config/staging/default.yaml` owns source roles, filename patterns, and
  outputs, but no raw source locations.
- `config/environments/base.yaml` defines one `infrastructure.data_root`,
  source subdirectories (`bm_dir`, `ndbd_mc_dir`, `bkg_mc_dir`), and output
  paths. Local and NERSC profiles override some values.
- Raw data, MC, JAGS products, and outputs may live on separate filesystems or
  under different roots. The current path resolver assumes relative paths are
  rooted at the same data root.
- The newer config builder resolves source paths from the environment tier;
  the legacy builder has separate path behavior and remains in use.

### Direction

Keep **physical paths environment-owned**, while `staging.yaml` owns the
**logical raw-source contract**. A staging source should identify its role,
pattern, and expected tree/branch contract, and reference a logical environment
root (for example `root_key: bkg_mc`). Environment profiles map each logical
root—data, background MC, signal MC, JAGS, and output as appropriate—to an
absolute or data-root-relative path.

Do not put machine-specific absolute paths in a reusable staging profile, and
do not require raw inputs and outputs to be children of one root. Use one
resolver with documented precedence and test separate raw/output roots.

Before implementation, confirm actual local and Perlmutter layouts and whether
JAGS files are staging inputs or downstream fit/prior inputs. See the linked
plan for the broader config ownership and study/API work.

## 2. Staging identity reminder

The current storage-input code uses `cfg.staging.version` as a string in
template hashes/metadata. The staging runner writes to a configured shared
directory; it does not publish a manifest or validate compatibility before
reuse.

Implement the full identity and publication design in the linked plan. At a
minimum, a `staging_id` must distinguish the resolved staging contract and raw
source identities (not just a manually assigned version or directory path).
Store a manifest with inputs, resolved cuts/transforms/schema, creation
provenance, and output counts/schema. Publish immutable stage artifacts, verify
the manifest/schema on reuse, and record the exact `staging_id` in every
downstream input/observation/template manifest. Model ROI/binning and fit-only
settings must not change the stage identity unless they change staged content.

when declared in typed config/schema, visible in dry-run output, and recorded in
the resolved manifest. Otherwise require the value or raise an actionable
error.

## 4. Legacy runner and launcher retirement inventory

The end-state target is that analysis behavior can be invoked through the
resolved-spec/planner API without depending on `qpym2/run` modules or
TSV-specific launch glue. Treat the following as migration/compatibility
surfaces and remove them after parity tests and consumer review; do not delete
them before their behavior, outputs, and callers are accounted for. The detailed
API migration and identity prerequisites are in the linked plan.

### `qpym2/run/`

- `run_create_staging.py` — raw-to-stage operation (deprecated).
- `run_create_input.py` — legacy histogram/input grid.
- `run_create_storage_inputs.py` — v0.6 storage-input CLI.
- `run_single_fit.py`, `run_single_storage_fit.py` — fit entry points.
- `run_fits.py` — TSV/local-pool fit launcher.
- `run_study.py` — v0.6 study CLI; replace with planner/API invocation first.
- `run_toy_batch.py`, `run_toy_fits.py` — toy launchers.
- `run_syst_lss.py`, `run_syst_mc.py`, `run_ndbd_shift_syst.py` — legacy
  systematic launchers. Their algorithmic redesign is out of scope here.
- `run_bin_size_fits.py`, `run_bin_size_bias_fits.py` — specialized matrix
  launchers; transfer supported behavior to explicit study/method definitions
  first.
- `run/__init__.py` — remove runner catalog/references after runner retirement.

### Related launch/config compatibility code

- Parameter/command generation and result collection:
  `scripts/gen_params.py`, `scripts/gen_syst_params.py`,
  `scripts/collect_results.py`, `scripts/run_params_seq.py`,
  `scripts/run_threshold250_bias.py`.
- Scheduler wrappers: `scripts/run_job.sh`, `scripts/submit.sh`,
  `scripts/submit_packed.sh`, `scripts/submit_syst.sh`, and corresponding
  `scripts/slurm/*.slurm` files. Do not submit jobs during this migration.
- Legacy configuration adapters/helpers:
  `qpym2/cfg/hydra_adapter.py`, `config_builders.py`, `model_utils.py`,
  `params_grid.py`, `toy_config.py`, `syst_config.py`, and `cfg/__init__.py`
  exports. Remove after imports/callers move to the supported config boundary.
- Generated/committed `scripts/params/*.tsv` and active docs/examples showing
  runner commands: classify as generated outputs or historical records, then
  update/remove per repository policy after the planner is operational.

Preserve reusable scientific algorithms and I/O/storage primitives. This is a
retirement of duplicated orchestration/config/launcher glue, not blanket
deletion of `qpym2.fit`, `qpym2.models`, `qpym2.io`, or `qpym2.storage`.

## 5. Completion conditions

- Physical raw roots are configurable independently of analysis output roots;
  staging YAML owns source roles/contracts, not machine-specific paths.
- Stages have validated immutable identities/manifests, and downstream
  products record their exact staging dependency.
- Hidden model/config fallbacks are removed or formalized in typed config and
  surfaced in resolved requests.
- Every runner/launcher in the retirement inventory is removed or has a named
  remaining consumer and owner. No production workflow depends on a hidden
  first-model choice, undeclared scientific default, or notebook-local path
  reconstruction.
